## Падение модели на длинном запросе через CUDA/RPC

На двух физических ПК с четырьмя CUDA/RPC-устройствами и сборкой llama.cpp b12318 (7021f7e09) выполнены три изолированных запуска пользовательской модели в Q4_K_M. Общие параметры: окно 131072, один слот, batch 256 / microbatch 128, Flash Attention включён; prompt — 6761 токен. Профиль пользователя и ключи не использовались в текстовых отчётах; запросы содержали синтетические данные.

| Проверка | Результат |
| --- | --- |
| q8_0/q8_0, прямо в backend, без шлюза и Effort | После обработки 4096 токенов удалённый RPC завершился с CUDA `an illegal memory access was encountered`; RPC восстановлен после сохранения журнала |
| f16/f16, прямо в backend, остальные параметры сохранены | HTTP 200, весь вход обработан, RPC остался доступен |
| f16/f16, через inference-шлюз, `reasoning_effort: on` | Маркер `OLC_EFFORT_FALLBACK`, HTTP 200, итоговый ответ READY, 31 выходной токен с рассуждениями, RPC остался доступен |

В третьем запуске обработка входа заняла 9,42 с, генерация — 1,91 с (15,71 токена/с). Загрузка модели занимала около 43 с. Эти проверки подтверждают проблему конкретной комбинации модели, типов кэша и сборки. Отдельное влияние K и V не изолировалось; заполнение всех 131072 токенов и длительный сеанс внешнего клиента не проверялись.

Регрессионный тест подтвердил, что строка ошибки подключения с адресом RPC ошибочно разрешала запуск модели; до исправления он падал. Теперь подтверждением служат только разобранные строки устройств. Четыре регрессии профилей нагрузки сначала обнаружили принудительную замену f16/Flash Attention на q8_0/включено; теперь профили сохраняют выбранные значения, включая явно заданный q8_0. Проверены реальные CLI-аргументы, применение в UI и сохранение/восстановление.

Итоговая Release-сборка прошла без ошибок и предупреждений. Целевая группа — 54/54, весь набор после согласования UI-проверок с сохранением f16 — 240/240 без пропусков. Валидатор документации и `git diff --check` прошли. Прежний единичный сбой удаления временного каталога в ClientEffortTests в целевой и итоговой проверках не повторился. После испытаний подтверждено, что удалённый RPC работает; тестовые процессы модели завершены.

Пока Desktop был закрыт, в пользовательском профиле изменены только CacheTypeK/CacheTypeV на f16/f16, исходный файл сохранён в резервную копию. Окно 131072, выход 32768 и batch 256/128 сохранены. Публикация и замена пользовательских бинарных файлов не выполнялись.

## Локальная копия GGUF и кэш RPC

Перед реализацией четыре проверки LocalModelCacheTests падали на отсутствии отпечатков, кэша, обработки split-GGUF и отмены. UI-проверка падала из-за отсутствия поля локальной модели на странице агента. После реализации проверяются реальные размеры и SHA-256, несовпадение байтов при одинаковом размере, неверный размер/число частей, отсутствие части, выбор не первой части, точные байты тензора в кэше, повторное использование без перезаписи, восстановление удалённого файла кэша и отмена до подготовки.

Проверки Avalonia.Headless подтверждают выбор роли, доступность пути и кнопок, блокировку при работающем агенте и ролью главного ПК, сохранение пути в AgentSettings и отсутствие загрузки при выключенном запоминании. Через настоящий TLS/MagicOnion проверены объявление локальной копии, передача выбранного пути дочернему Agent через окружение, проверка SHA-256 и понятный FailedPrecondition при несовпадении, отказ при неверном ключе и при выключенном удалённом управлении. Отдельный тест команды главного Desktop подтвердил, что несовпадение модели на узле не позволяет создать процесс llama-server.

С официальной Windows CPU-сборкой b12318 выполнена отдельная нативная проверка на loopback. Синтетический корректный GGUF содержал один F32-тензор 12 MiB. NativeGgufLayout определил смещение 64 и длину 12582912; RpcModelCache подготовил файл штатного RPC-кэша. Настоящий ggml-rpc-server запущен с этим LLAMA_CACHE и --cache. Нативный RPC-клиент выделил удалённый буфер весов и передал тензор; счётчик TCP-прокси зафиксировал **321 байт клиентского трафика** при загрузке **12582912 байт весов**. Контрольное чтение с RPC вернуло исходные данные. Собственный RPC-процесс завершён после проверки.

Это подтверждает совместимость формата кэша и чтение настоящим RPC без сетевой передачи всего тестового тензора. Загрузка полной пользовательской модели с локальных дисков разных ПК, эффект на её время старта и нативные Linux/macOS в этой проверке не измерялись. SHA-256 требует полного чтения GGUF при каждой сверке. Внутренний кэш использует FNV-1a и порог больше 10 MiB согласно [исходникам b12318](https://github.com/ggml-org/llama.cpp/blob/7021f7e09/ggml/src/ggml-rpc/ggml-rpc.cpp); меньшие, частичные или преобразованные блоки могут передаваться обычным путём. Персональные веса, текущие настройки пользователя и удалённые процессы в этой проверке не изменялись; публикация не выполнялась.

Итоговая Release-сборка завершена без ошибок и предупреждений; целевая группа прошла 16/16, весь набор — 249/249 без пропусков. Дополнительно нативное чтение GGUF проверено с кириллицей в имени файла. Проверки локальных ссылок, изменённых строк C# и `git diff --check` пройдены.

Приёмка на двух ПК: обновить Desktop/Agent на узле, выбрать совпадающий локальный GGUF, подготовить кэш, запустить TLS-агент и RPC, затем запустить движок главного ПК. Проверить статус сверки и загрузку модели; повторить с отличающимся файлом и убедиться, что ошибка SHA-256 блокирует запуск. После возврата совпадающей модели проверить повторный запуск с готовым кэшем.

## Автоматический подбор GPU-слоёв вместо фиксированных 99

Из памяти работающего Desktop прочитаны параметры и журнал неудачной загрузки пользовательской модели в Q8_0. Фактическая ошибка — cudaMalloc: недостаточно памяти для ещё 3072 MiB KV-cache, затем failed to create context. Предшествующее предупреждение `n_gpu_layers already set by user to 99, abort` означало отказ fit менять явно заданное число слоёв, а не отдельный конфликт повторных CLI-аргументов. RPC оставался доступен, локальная копия GGUF была успешно сверена.

Перед исправлением три регрессии падали: исходное значение оставалось 99, планировщик запрещал -1, редактор не позволял выбрать авто. Теперь -1 формирует `--n-gpu-layers auto --fit on --fit-target` с резервом устройств и без ручного tensor-split, который также блокирует перераспределение. Список устройств, контекст, слоты и точность кэша сохраняются. Ручные значения 0/20/99 и их tensor-split проверены отдельно; значения ниже -1 запрещены. Авто восстанавливается через настоящий редактор Avalonia и профиль. Ранее сохранённые ручные значения не мигрируются молча.

На той же пользовательской модели выполнен изолированный запуск через новый планировщик с контекстом 131072, восемью слотами, batch 512 / microbatch 128 и f16/f16. При сохранённом списке четырёх CUDA/RPC-устройств режим auto позволил загрузить модель примерно за 54 с. Авторизованный запрос через шлюз вернул HTTP 200 и READY: 8311 входных, 35 выходных токенов с рассуждениями; prompt 66,62 с, генерация 10,15 с (3,35 токена/с). RPC после запроса остался работать. Тестовый движок завершён, исходный Desktop продолжает работать; профиль и пользовательские бинарные файлы не менялись. Это подтверждает исправление конкретного запуска, но не заполнение всего окна и не оптимальную скорость. Размещение части вычислений/весов в RAM может замедлять работу; выбор меньшего окна и меньшего числа слотов требует отдельного замера.

Итоговая Release-сборка прошла без ошибок и предупреждений. Целевые проверки — 19/19; весь набор после явного выбора ручного режима в тесте tensor-split — 255/255 без пропусков. Валидатор документации и `git diff --check` пройдены.

Семантика auto и ограничения явного tensor-split сверены с исходниками закреплённой [сборки b12318](https://github.com/ggml-org/llama.cpp/blob/7021f7e09/common/fit.cpp). Релиз не публиковался.

Отмена скачивания и «Позже» проверены при реальных дочерних процессах Fixture-движка и RPC в обеих ролях; процессы и порты остаются доступны. Ошибки чтения исходного профиля и startup-файла блокируют применение без перезаписи данных.

[VelopackDownloadTests](tests/OpenLLMCluster.Tests/VelopackDownloadTests.cs) дополнен проверкой отсутствующего обновлятора: готовый пакет остаётся на диске, подготовка и выход приложения не начинаются. Существующие [SafeUpdateTests](tests/OpenLLMCluster.Tests/SafeUpdateTests.cs), проверки интерфейса и адаптера покрывают отдельное подтверждение, блокировки на время применения, порядок остановки и сохранения, повреждённый пакет, отмену, сеть, повтор, каналы и версии.

При публикации тестовой версии выявлена ошибка: `Push-Location` PowerShell не меняет текущий каталог .NET, поэтому относительный `-ReleaseRoot` зависел от места запуска процесса. До исправления новый тест [PublicationTests](tests/OpenLLMCluster.Tests/PublicationTests.cs) получил путь вне ожидаемого корня; после явного указания базы в `Path.GetFullPath` тест прошёл. Проверка использует `-ValidateOnly` и не создаёт выпуск.

**Полные прогоны:** Windows — **370/370**, без пропусков; Linux Ubuntu 24.04 под WSL — **352 успешных**, **17 пропущенных**, **0 ошибок**. Пропуски Linux относятся к Windows Firewall и Windows-установщикам/runtime recovery. Сборки на обеих ОС завершились с **0 ошибок и 0 предупреждений**. Linux использовал отдельную копию исходников, чтобы сборки разных ОС не записывали одни и те же bin/obj.

**Настоящее применение пакетов A → B:** из отдельного снимка исходников с временной версией 0.2.299 подготовлены Windows/Linux-пакеты A. Штатные Update.exe и UpdateNix применили существующие full-пакеты 0.2.300 к изолированным копиям A. Основная версия проекта не менялась, проверочный A не публиковался. Windows portable обновила manifest, Desktop и Agent до 0.2.300; DLL совпали с целевой публикацией, hooks obsolete/updated завершились с кодом 0. Linux заменил AppImage, его SHA256 совпал с целевым B.

Из обновлённых файлов на обеих ОС запущены Desktop bootstrap, Agent и inference-шлюз: bootstrap завершился с кодом 0, шлюз вернул 401 без ключа и 204 с ключом, Agent — HTTP/2 401 без ключа. Все процессы диагностического запуска завершены. Хеши пользовательских файлов до и после совпали, рабочая установка не заменялась, системные runtime не устанавливались. Тестовые пакеты хранятся отдельно от штатного комплекта выпуска, диагностика находится вне репозитория.

**Ограничения:** применение проверено нативным CLI обновлятора, перезапуск — аргументом быстрого bootstrap без обычного окна. Подтверждение/остановка/сохранение и восстановление профиля проверены отдельно в Headless-тестах; сквозной сценарий настоящего GUI через публичный GitHub ещё не выполнен. ## Диагностика запуска через inference-шлюз

Подключение ClrMD к работающему Desktop подтвердило HTTP 502 в последней ошибке и отсутствие работающего движка. Диагностический агент узла отвечал по TLS, но его вычислительный RPC был остановлен. Через авторизованный канал RPC запущен повторно; настоящий llama-server подтвердил два локальных и два удалённых CUDA-устройства одинакового build.

До исправления две проверки падали с HTTP 502: проверка готовности API и интеграционный запуск backend с отложенным открытием HTTP-порта через настоящий inference-шлюз. После исправления все 32 проверки EngineApiTests, EngineProcessTests, EngineShutdownTests и ClientEffortTests прошли без пропусков. HTTP 502 во время ожидания /health означает «ещё не готов»; авторизация, общий таймаут, отмена и раннее завершение процесса продолжают проверяться.

На двух физических Windows-ПК отдельно подтверждены загрузка пользовательской модели в Q4_K_M с текущим окном 16384, q8_0 KV-cache, Flash Attention и четырьмя CUDA/RPC-устройствами, авторизованная готовность API и генерация 32 токенов через шлюз. Загрузка заняла около 44 секунд. Тестовый движок остановлен, его API-порт освобождён; исходное окно Desktop и пользовательский профиль не изменялись. В ходе заключительной проверки оба TCP-порта узла временно перестали отвечать при доступном ICMP ping. После восстановления доступа агент вернул исходное пустое состояние RPC; вычислительный процесс повторно запущен авторизованной командой, настоящий llama-server снова подтвердил оба удалённых CUDA-устройства. Состояние включённого компьютера и работающего Desktop само по себе не подтверждает запуск отдельного вычислительного RPC. Это проверка запуска и короткой генерации, не проверка окна 128K или качества длинного диалога.

При предварительной проверке с очень маленьким тестовым GGUF обнаружен отказ CUDA Flash Attention в llama.cpp (`BEST_FATTN_KERNEL_NONE`). Повтор с Flash Attention, отключённым только в тестовом профиле, прошёл; пользовательская модель затем успешно проверена с исходным включённым Flash Attention. Публикация не выполнялась; уже работающий Debug-процесс продолжает использовать прежнюю сборку до перезапуска с пересборкой.

## Ручная приёмка установки и запуска кластера

1. На каждом ПК развернуть всю новую публикацию Desktop вместе с Agent и локально установить один и тот же build/backend по [подробному руководству](README-DEV.md#запуск-кластера). Для NVIDIA выбрать CUDA. Проверить ошибку недоступного build и отмену загрузки с повторной попыткой.
2. На сетевом узле включить LAN агента, запустить его, выбрать роль Worker, адрес RPC интерфейса или 0.0.0.0 и порт. Создать RPC-правило с UAC; повторное нажатие не должно дублировать правило. Проверить отмену UAC.
3. Запустить RPC, убедиться в журнале, проверить TCP с главного ПК. Локальная TCP-готовность Worker не заменяет проверку устройств главным процессом.
4. На главном ПК выбрать тот же build, указать GGUF и включённые узлы с ключами. Проверить отказ при неправильном ключе, другом build или выключенном RPC. Для возврата на прежний build использовать повторную установку существующей версии.
5. Запустить главный сервер. В журнале должны появиться RPC-устройства, затем загрузка модели. Статус готовности должен появиться только после /health и авторизованного /v1/models. При нехватке памяти уменьшить контекст или GPU-слои и повторить.
6. Нажать контрольный запрос и получить фактический ответ; подключить OpenAI-compatible client с алиасом open-llm-cluster, URL главного ПК и отдельным ключом API. Для сетевого клиента отдельно разрешить API-порт главного ПК.
7. Во время долгой загрузки проверить отмену и остановку: собственный процесс и порт освобождаются; занятый чужой порт не должен приводить к завершению чужой программы.
8. Проверить остановку, повторный старт и закрытие Desktop на обеих ролях; ключи не должны сохраняться в профиле или журнале, несекретные параметры должны восстановиться согласно переключателю. После перезапуска потребуется новый ключ API либо ручной ввод прежнего.
9. Проверить локализацию и читаемость установки/журнала/управления на обоих языках. Кнопки на вкладке «Журнал» затрагивают оба журнала, кнопки у llama.cpp — только вывод движка; процессы сохраняются.

После автономных тестов новые задачи остаются в статусе ожидания пользовательской приёмки; порядок отражён в [TODO.md](TODO.md).

## Безопасное применение обновления

[SafeUpdateTests](tests/OpenLLMCluster.Tests/SafeUpdateTests.cs) сначала воспроизвёл отсутствие подключённого установщика, затем проверил отдельное подтверждение, повторную проверку пакета до остановки работы, отказ при ошибке сохранения/запуска обновлятора, отмену подготовки и запрет параллельных операций. В настоящем XAML-окне проверены блокировка рабочих вкладок и закрытия на время подготовки, восстановление доступа после ошибки.

Селфтесты запускают отдельные процессы Fixture-движка в ролях главного ПК и узла, а также настоящий дочерний Agent. До вызова адаптера проверяются завершение процессов, закрытые порты API/RPC и агента, сохранённые геометрия и защищённые ключи, отсутствие секретов в профиле. Посторонний TCP-listener остаётся доступен, файлы модели и runtime не меняются. Проверены выключенное запоминание настроек и выключенное запоминание ключей. Реальный `UpdateManager` на подменённом источнике отдельно отклоняет пакет, изменённый на диске после скачивания, ещё до подготовки приложения.

Применение и перезапуск проверяются адаптером без замены работающей установки. Это подтверждает порядок подготовки и обработку отказов; настоящее обновление установленной версии A до B и восстановление после перезапуска ещё требуют отдельной проверки на целевых ОС. Приложение не обещает автоматический откат версии или профиля.

## Платформенная упаковка

[PlatformPackagingTests](tests/OpenLLMCluster.Tests/PlatformPackagingTests.cs) до реализации обнаружил отсутствие скрипта упаковки и ICNS. После реализации прошли **11/11** проверок: планы четырёх RID, каналы, платформенные зависимости/иконки, неподписанный ZIP для macOS, отказ при неполном Agent, неверной версии/канале, встроенном runtime и пользовательских файлах, блокировка упаковки на чужой ОС. Проверена структура ICNS и размеры PNG 128/256/512/1024.

Нативная проверка Linux обнаружила реальную ошибку: vpk успешно создавал AppImage с xz, но его runtime отказывался распаковывать этот формат. Регрессия сначала падала; упаковка переключена на gzip и дополнена обязательной самораспаковкой AppImage с проверкой наличия Desktop и вложенного Agent. Сам факт успешной работы упаковщика больше не считается достаточным результатом.

Подготовлены пакеты версии **0.2.300**: Windows Setup **23,29 МиБ**, portable ZIP **16,08 МиБ**, full **16,10 МиБ**; Linux AppImage **15,34 МиБ**, full **14,85 МиБ**. Для обоих каналов созданы индексы и `SHA256SUMS`; размер и SHA256 full-пакетов совпадают с индексами. В Windows full-пакете сохранены обе зависимости внешнего runtime.

Из распакованного Windows portable реально открыто окно Desktop с ожидаемой версией, запущены Agent и inference-шлюз. Из Linux AppImage, собранного в Ubuntu 24.04 x64 под WSL, выполнены самораспаковка, запуск AppRun в режиме extract-and-run с быстрым bootstrap-hook Desktop до UI, запуск Agent и inference-шлюза. На обеих ОС агент подтвердил HTTP/2 с ответом 401 без ключа, шлюз — 401 без ключа и 204 с ключом. Host trace подтвердил внешний .NET 10 для всех компонентов; проверочные процессы завершены, существующие профили не изменены. Работа окна Linux, FUSE-монтирование, реальная модель и GPU на Linux этой проверкой не подтверждены.

Для `osx-arm64` и `osx-x64` подготовлены framework-dependent файлы, ICNS и проверенные планы упаковки с bundle ID и `--noInst`. Нативные macOS ZIP/full/индексы не создавались: нужен Mac. Finder, Gatekeeper, обе архитектуры, Agent и llama.cpp остаются частью приёмки на macOS. Не проверены установка Windows Setup на чистой ОС и обновление A → B на всех платформах.
